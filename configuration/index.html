    Configuration¶

    The gateway must be configured using the file application.properties which is available under path ./src/main/resources. Please note that a copy of the contents of this resources folder in embedded into the GraalVM binary, in any case and must be overloaded using an external configuration file via docker volume as shown in the corresponding docker compose files.

    Configuration Files¶

    Different configuration profiles were developed for configuration and testing within IntelliJ IDEA for sender and receiver. The corresponding files are:

    • application.properties (main default config for debugging directly in IntelliJ IDEA)
    • application-receiver.properties
    • application-sender.properties
    • application-tls-in-on.properties (profile that activates incoming tls config)
    • application-tls-out-on.properties (profile that activates outgoing tls config)
    • docker.properties (is loaded externally docker-compose script.)

    Please edit config in docker-compose file as otherwise the config will be overwritten.

    Gateway Role¶

    This switch lets the gateway act as sending gateway. Options are either SENDER or RECEIVER. 

    gatewayRole=SENDER

    Sender Gateway Properties¶

    These entries specify the destination domain and port of the receiving gateway where messages must be forwarded to.

    gatewayDomainRC=localhost
gatewayPortRC=8081

    These entries specify self-information for the gateway, needed for alert entry enrichment, for instance. 

    gatewayDomainSD=localhost
gatewayPortSD=8080

    Receiver Gateway Properties¶

    These entries identify where the local Kafka database can be found. 

    kafkaDomainLocal=kafkalocal
kafkaPortLocal=8082

    SSL Activation or Deactivation (DEBUG Connection Settings)¶

    The gateway has a setting to control the inbound SSL configuration (Spring boot VM settings), and the outbound SSL configuration (Java internal SSL Context object). Both can be activated or deactivated separately using the following flags in docker-compose.

          GATEWAY_PROTOCOL: https     # for communication from gateway sender to gateway receiver
      SSL_INBOUND_ACTIVATED: true
      SSL_OUTBOUND_ACTIVATED: true

    For debug purposes in a testing environment the SSL-settings can be both be set to false. This means that neither the initial connection from the outside inside the Gateway-sender nor the forwarding from Gateway-sender to Geteway-receiver will apply HTTPS but only HTTP. This setting is not acceptable for a production environment but ONLY FOR TESTING PURPOSES!

    The file docker-compose-debug-http.yaml is properly configured to work out of the box and can be launched using:

    docker compose up -d rest-proxy control-center schema-registry broker 
docker compose -f docker-compose-debug-http.yaml up gateway-sender
docker compose -f docker-compose-debug-http.yaml up gateway-receiver

    Relevant Headers¶

    For information purposes the outgoing requests hold the role information as HTTP Headers. This array lists headers to be forwarded within the gateway. All other headers are dropped. 

    relevantHeaders={'content-type','accept','user-Agent','accept-Encoding','safe4soc-receiver-hostname','safe4soc-receiver-port'}

    Additional Endpoints for Debugging¶

    If configuration testing is required the following endpoints can be used to reload a configuration during runtime. However, they MUST BE DEACTIVATED in secure mode using the corresponding flags: 

    endpoints.reloadconfig.enabled: false
endpoints.setisa.enabled: false

    Information Sharing Agreement Configuration¶

    Filter Configuration¶

    The Filtering configuration uses a nested list in JSON format. Scalar filter rules use the configured replacement value. For an empty string (""), the gateway checks a candidate alert against the configured schema. It omits the field if the empty string introduces a validation error. An empty object clears the contents of the corresponding object or array for supported nested filters. For Analyzer, Sensor, Source, and Target, a blank rule applies to the named field and preserves the rest of the entry. A nonempty string rule for Sensor, Source, or Target replaces the existing IP addresses in the array. The gateway validates the alert against the configured IDMEFv2 schema before ISA processing and again after filtering and enrichment. If either validation fails, the gateway returns HTTP 422 and stops forwarding.

      "filterConfig": {
    "CreateTime": "",
    "StartTime": ""
  },

    Enrichment¶

    The enrichment configuration uses a nested list in JSON format, also. However, each enrichment functionality must be implemented specifically. The class Utils contains a prepared nested case structure for all elements to individually implement an enrichment where necessary.

      "enrichmentConfig": {\
    "CreateTime": "",\
    "StartTime": ""\
  }\
}

    Currently, the feature is available to enrich alerts with missing timestamps. If it is missing the timestamp within the running gateway will be used as value in the same format for the CreateTime or StartTime field.

    Drop Configuration¶

    This JSON element inside the ISA lists elements that cause the forwarding of alerts to be completely dropped and aborted. If values that are configured here are found in an IDMEFv2 alert, the dropping is triggered.

      "dropConfig": {
    "Version": "",
    "ID": "",
    "Status": "",
    "OrganisationName": "",
    "CreateTime": "",
    "StartTime": "",
    "Cause": "",
    "Category": "",
    "Priority": "High",
    "Confidence": "",
    "Description": ""
  },

    As can be seen above, these fields can be used for drop configuration. If an alert is processed with a priority value "High" it will NOT be forwarded, but dropped.

    Required Configuration¶

    This JSON element inside the ISA lists elements that that must be non-empty values, otherwise the forwarding will be aborted. Please note this is distìnguished from filtering configuration.

      "requiredConfig": {
    "Version": "",
    "ID": "",
    "StartTime": "",
    "Status": "",
    "Source": "",
    "Target": ""
  }

    Updating the ISA via REST Endpoint¶

    Two ways exist to update the gateway configuration ONLY IN DEBUG MODE for security reasons: 1. via Rest API call to /setisa 2. via change of application.properties file and a Rest API call to /reloadconfig

    The following example sets an ISA which filters the source IP addresses: 

    curl --location 'localhost:10080/setisa' \
--header 'Content-Type: application/json' \
--data '{
    "provider_reason": "compliance",
    "intended_use": "alert_gathering",
    "data_usage_policies": {
        "use_until": "2024-12-12",
        "use_after": "2024-09-12",
        "share_further": "false"
    },
    "data_sender_SIEM_brand": "Example Company A",
    "data_sender_SIEM_version": "Version 0.1",
    "IDMEFv2_attributes": {
        "attributes_to_transmit": [],
        "attributes_to_neglect": [],
        "attributes_to_anonymize": [],
        "attributes_to_pseudonemize": []
    },
    "sending_mode": "",
    "encryption_requirements": [],
    "authentication_requirements": [],
    "connection_requirements": [],
    "filterConfig": {
            "Source": {
              "IP": ""
            }
    },
    "enrichmentConfig": {
    }
}'

    IDMEFv2 Schema Configuration¶

    The IDMEFv2 Schema is very important, as it contains the acceptance rules for the incoming JSON structure of alerts. If no external IDMEFv2.json file is found under the specified "IDMEFv2SchemaPath" by default a standard schema embedded into the GraalVM compiled binary will be used.
